# План демонстрации разработанного программного продукта

## wal-g binlog-server для восстановления MySQL на точку во времени

### 1. Назначение демонстрации

Цель демонстрации - показать работу разработанного режима `wal-g binlog-server` при восстановлении базы данных MySQL на заданную точку во времени. Основной акцент делается не на факте наличия Point-in-Time Recovery как такового, а на более эффективном применении бинарных логов после восстановления полной резервной копии.

Во время демонстрации необходимо показать, что разработанный подход позволяет:

- применять binary log без предварительного преобразования в цельный SQL-файл;
- передавать события MySQL постепенно через протокол репликации;
- сократить использование временного дискового пространства;
- работать с большими binlog-файлами, в том числе размером более 15 ГБ;
- выполнять восстановление до заданной точки при сохранении целостности данных.

Отдельно следует подчеркнуть, что `wal-g binlog-server` не является отдельным web-интерфейсом или самостоятельным пользовательским CLI. Демонстрируется именно режим работы WAL-G, который требует предварительной настройки окружения перед запуском восстановления.

### 2. Состав демонстрационного стенда

Для демонстрации используется изолированный тестовый стенд. Он должен быть подготовлен заранее, чтобы во время выступления не тратить время на установку пакетов и первичную настройку MySQL.

| Компонент | Назначение | Что должно быть подготовлено |
|---|---|---|
| MySQL-источник | Формирование тестовых данных и binary log | Включены `log_bin`, `server_id`, GTID или зафиксирована позиция binlog |
| Хранилище backup/binlog | Хранение полной копии и бинарных логов | Настроен доступ WAL-G к каталогу или объектному хранилищу |
| Восстанавливаемый MySQL | Целевой инстанс для демонстрации PITR | Пустой или заранее очищенный экземпляр MySQL |
| WAL-G с разработанным режимом | Запуск восстановления через `wal-g binlog-server` | Собранная версия WAL-G с поддержкой режима |
| Набор тестовых данных | Проверка корректности восстановления | Таблица с контрольными строками и транзакциями |

### 3. Предварительная подготовка перед демонстрацией

Перед началом демонстрации необходимо выполнить техническую подготовку стенда. Эти действия лучше сделать заранее и во время защиты только кратко показать результат.

1. Проверить наличие собранного бинарного файла WAL-G с поддержкой `binlog-server`.
2. Подготовить MySQL-источник с включенным бинарным журналированием.
3. Создать тестовую базу данных и наполнить ее начальными данными.
4. Выполнить полную резервную копию базы данных.
5. Сгенерировать несколько изменений после создания полной копии.
6. Сохранить binary log в хранилище, доступное WAL-G.
7. Подготовить отдельный MySQL-инстанс для восстановления.
8. Проверить параметры подключения, права пользователя и сетевую доступность.
9. Подготовить контрольные SQL-запросы для проверки результата.

Желательно иметь два сценария: короткий демонстрационный сценарий на небольшом объеме данных и отдельное подтверждение работы с крупными binlog-файлами. Для крупного сценария достаточно показать подготовленный результат или заранее снятые измерения, так как применение binlog размером более 15 ГБ может занять значительное время.

### 4. Требования к настройке MySQL

На стороне MySQL должны быть включены параметры, необходимые для работы с бинарными логами и репликационным протоколом. Конкретные значения могут отличаться в зависимости от стенда, но для демонстрации важно зафиксировать следующие настройки:

```ini
[mysqld]
server_id=1
log_bin=mysql-bin
binlog_format=ROW
gtid_mode=ON
enforce_gtid_consistency=ON
```

Если демонстрационный стенд не использует GTID, необходимо заранее зафиксировать имя binlog-файла и позицию начала восстановления. В докладе можно отметить, что оба подхода применимы, но для повторяемой демонстрации удобнее использовать заранее подготовленные значения.

Также необходимо подготовить пользователя MySQL с правами, достаточными для подключения и работы через репликационный протокол. В демонстрационном документе пароль не указывается; при показе он должен храниться в переменных окружения или конфигурации стенда.

### 5. Требования к настройке WAL-G

Перед запуском восстановления должны быть заданы параметры доступа к хранилищу резервных копий и binary log. В демонстрации можно использовать локальный каталог или объектное хранилище. Важно, чтобы путь к backup и binlog был одинаково доступен для команд WAL-G.

Пример набора переменных окружения для демонстрационного стенда:

```bash
export WALG_MYSQL_DATASOURCE_NAME='user:password@tcp(127.0.0.1:3306)/mysql'
export WALG_FILE_PREFIX='/tmp/walg-demo'
export MYSQL_HOST='127.0.0.1'
export MYSQL_PORT='3306'
```

Набор переменных может быть изменен под конкретный стенд. Важно показать не сами секреты доступа, а факт, что перед запуском `wal-g binlog-server` окружение должно быть заранее настроено.

### 6. Демонстрационный сценарий

#### Этап 1. Показ исходного состояния

На первом этапе демонстрируется исходная база данных до сбоя или ошибочного изменения. Следует показать тестовую таблицу и контрольные записи.

Пример контрольного запроса:

```sql
SELECT id, operation_name, created_at FROM demo_operations ORDER BY id;
```

Ожидаемый результат: в таблице есть начальные записи, которые затем войдут в полную резервную копию.

#### Этап 2. Создание полной резервной копии

Далее показывается, что полная резервная копия уже создана или создается командой WAL-G. В рамках защиты достаточно показать наличие backup в хранилище и зафиксировать, что это базовая точка восстановления.

Пример команды:

```bash
wal-g backup-push /var/lib/mysql
```

После этого необходимо показать список резервных копий:

```bash
wal-g backup-list
```

#### Этап 3. Генерация изменений после backup

После создания полной копии в базу добавляются новые изменения. Они нужны, чтобы показать смысл Point-in-Time Recovery: база должна быть восстановлена не только до состояния backup, но и до выбранного момента после него.

Пример:

```sql
INSERT INTO demo_operations(operation_name, created_at)
VALUES ('correct operation before failure', NOW());

INSERT INTO demo_operations(operation_name, created_at)
VALUES ('wrong operation after target point', NOW());
```

Перед демонстрацией следует заранее определить целевую точку восстановления: например, момент после первой операции, но до второй ошибочной операции.

#### Этап 4. Имитация ошибки или потери данных

Для наглядности можно выполнить ошибочное изменение, которое должно отсутствовать после восстановления. Например, удалить часть записей или добавить некорректную запись.

```sql
DELETE FROM demo_operations WHERE operation_name = 'correct operation before failure';
```

После этого демонстрируется, что текущее состояние базы отличается от ожидаемого и требуется восстановление.

#### Этап 5. Восстановление полной резервной копии

На целевой MySQL-инстанс восстанавливается полная резервная копия. Этот этап можно показать кратко, так как основной предмет демонстрации - применение binary log через `wal-g binlog-server`.

Пример команды:

```bash
wal-g backup-fetch /var/lib/mysql LATEST
```

После восстановления полной копии база находится в состоянии на момент backup. Следующий этап - доведение ее до нужной точки с помощью binlog.

#### Этап 6. Запуск `wal-g binlog-server`

На этом этапе запускается разработанный режим. Его задача - отдавать восстанавливаемому MySQL-инстансу события binary log через протокол репликации, без предварительного преобразования всего binlog в SQL.

Пример запуска следует адаптировать под фактические параметры реализации:

```bash
wal-g binlog-server \
  --from-binlog mysql-bin.000001 \
  --to-time '2026-05-22 12:30:00'
```

Во время показа необходимо пояснить, что binary log загружается по мере необходимости. После применения обработанные файлы могут удаляться, поэтому на диске не требуется хранить всю цепочку binlog одновременно.

#### Этап 7. Подключение восстанавливаемого MySQL через репликационный протокол

Восстанавливаемый MySQL-инстанс получает события от `wal-g binlog-server` как от источника репликации. За счет этого не создается большой промежуточный SQL-файл, а применение идет последовательно.

В докладе важно подчеркнуть отличие от подхода с преобразованием binlog в SQL:

- нет единого крупного SQL-файла;
- меньше временных файлов;
- ниже требования к свободному месту на диске;
- лучше подходит для больших binlog-файлов.

#### Этап 8. Проверка результата восстановления

После завершения применения binlog выполняются контрольные SQL-запросы. Они должны показать, что база восстановлена до выбранной точки.

Проверяется следующее:

- записи из полной копии присутствуют;
- корректные изменения после backup применены;
- ошибочные изменения после целевой точки отсутствуют;
- структура таблиц не повреждена;
- количество записей соответствует ожидаемому результату.

Пример:

```sql
SELECT COUNT(*) FROM demo_operations;
SELECT * FROM demo_operations ORDER BY id;
```

### 7. Отдельный акцент на больших binlog

Для демонстрации преимущества решения желательно заранее подготовить материал по сценарию с большим binlog-файлом. На предзащите или защите не обязательно полностью применять файл размером более 15 ГБ в реальном времени. Достаточно показать подготовленную статистику или лог выполнения.

В этом фрагменте следует показать:

- размер исходного binlog-файла;
- отсутствие преобразования в цельный SQL;
- последовательную загрузку и применение;
- отсутствие необходимости хранить все binlog локально одновременно;
- пример использования дискового пространства во время работы.

Рекомендуемый вывод для демонстрации: разработанный подход особенно полезен не на малых тестовых данных, а при реальных объемах binary log, когда промежуточная конвертация в SQL становится дорогой по времени и месту на диске.

### 8. Критерии успешной демонстрации

Демонстрация считается успешной, если выполнены следующие условия:

| Критерий | Ожидаемый результат |
|---|---|
| Полная копия восстановлена | MySQL запускается после восстановления backup |
| Binary log применен до заданной точки | В базе есть изменения до целевого момента |
| Ошибочные изменения не применены | Данные после целевой точки отсутствуют |
| Нет преобразования в цельный SQL | Временный SQL-файл не создается |
| Binlog обрабатываются постепенно | Файлы загружаются и применяются последовательно |
| Снижено использование диска | Не требуется локально хранить всю цепочку binlog |
| Большие binlog поддерживаются | Сценарий с файлом более 15 ГБ не требует цельной SQL-конвертации |

### 9. План выступления во время демонстрации

| Время | Действие | Комментарий докладчика |
|---|---|---|
| 0:00-0:30 | Кратко описать цель показа | Демонстрируется не обычный backup, а ускорение этапа применения binlog |
| 0:30-1:30 | Показать исходную базу и backup | Полная копия является базой для PITR |
| 1:30-2:30 | Показать изменения после backup | Эти изменения должны попасть в восстановленную базу до заданной точки |
| 2:30-3:30 | Показать ошибочное изменение | Оно должно отсутствовать после восстановления |
| 3:30-5:00 | Запустить восстановление и `wal-g binlog-server` | Основной акцент - применение через протокол репликации |
| 5:00-6:00 | Выполнить контрольные SQL-запросы | Проверяется корректность результата |
| 6:00-7:00 | Показать выводы по скорости и диску | Нет цельного SQL-файла, меньше временного места, поддержка больших binlog |

### 10. Что подготовить на случай технических проблем

Так как демонстрация связана с MySQL, резервными копиями и бинарными логами, необходимо заранее подготовить резервный вариант показа. Это особенно важно для защиты, где время ограничено.

Рекомендуется иметь:

- заранее созданный backup;
- заранее сохраненные binlog;
- скрипт наполнения тестовой базы;
- скрипт проверки результата;
- лог успешного запуска `wal-g binlog-server`;
- скриншоты или текстовый вывод для сценария с binlog более 15 ГБ;
- архив с конфигурацией демонстрационного стенда;
- короткую версию сценария на 3-4 минуты.

Если live-демонстрация не запускается, можно показать заранее подготовленные выводы команд и объяснить последовательность работы по ним. В этом случае основной акцент остается на архитектурном решении и устранении проблем скорости и временного диска.

### 11. Краткий чек-лист перед выступлением

Перед началом демонстрации необходимо проверить:

- MySQL-источник запущен;
- целевой MySQL-инстанс доступен;
- binary log включены и доступны;
- резервная копия присутствует в хранилище;
- WAL-G запускается без ошибок;
- переменные окружения заданы;
- тестовые SQL-запросы подготовлены;
- порт для `wal-g binlog-server` свободен;
- есть свободное место на диске для минимального набора временных файлов;
- подготовлен резервный сценарий демонстрации.

### 12. Итоговый тезис для завершения демонстрации

Разработанный режим `wal-g binlog-server` решает практическую проблему восстановления MySQL на точку во времени при больших объемах binary log. В отличие от сценария с преобразованием binlog в SQL, события применяются постепенно через протокол репликации. Это сокращает лишнюю обработку, уменьшает потребность во временном дисковом пространстве и делает восстановление более пригодным для крупных binlog-файлов. При этом инструмент требует предварительной настройки окружения, поэтому его корректная работа зависит от подготовленного стенда и правильно заданных параметров восстановления.
